# CU Launch Template Authoring

Templates are metadata-driven starter packages used by the portal to generate managed GitHub repository contents from a rendered source snapshot.

## Template Structure

Each template lives under `templates/<slug>/` and currently includes:

- `template.json` for manifest metadata
- `files/` for renderable starter files
- `.template` file extensions for source files that receive token replacement

Templates may also split output between:

- `entryFiles` in `template.json` for real on-disk template assets under `files/`
- `generatedFiles` in `template.json` for archive entries produced by code during generation
- `conditionalEntryFiles` in `template.json` for real on-disk assets included only when selected template features require them
- `generatedOverrides` in `template.json` for archive paths intentionally produced by generation code instead of same-path template assets

## Supported Tokens

Template files currently support these tokens:

- `{{APP_NAME}}`
- `{{APP_NAME_SLUG}}`
- `{{APP_DESCRIPTION}}`
- `{{HOSTING_TARGET}}`
- `{{APP_NAME_JS}}`
- `{{APP_DESCRIPTION_JS}}`
- `{{DATABASE_PROVIDER}}`, the selected database provider such as `postgresql` or `none`
- `{{ENTRA_LOGIN_ENABLED}}`, `true` when generated Microsoft Entra login is enabled
- `{{AZURE_RUNTIME_STACK}}`, the Azure App Service runtime stack such as `NODE|24-lts` or `PYTHON|3.14`
- `{{APP_SERVICE_RUNTIME}}`, the display runtime label such as `Node.js 24 / Next.js` or `Python 3.14 / FastAPI`

Use the `*_JS` tokens when rendering into JavaScript or JSX string-expression contexts so user input is escaped safely.

## Catalog Metadata

The in-code template catalog lives in `src/features/templates/catalog.ts`.

Each template entry defines:

- slug and display metadata
- `category`, either `recommended` for non-technical choices or `developer` for lower-level starters
- optional `sourceTemplateSlug` when a user-facing preset reuses another template's source files
- `decisionSummary`, a short chooser explanation for when to pick the template
- `bestFor`, a concise list of use cases shown with the template
- status (`ACTIVE` or `DISABLED`)
- the fields rendered in the create form
- `appServiceRuntime`, including the App Service runtime family, framework, Azure runtime stack, startup command, and workflow filename
- `features`, including database support and Microsoft Entra login support

Current active starter templates are grouped into Recommended Templates and Developer Starters. Recommended Templates are non-technical presets such as Department Form + Approval, Simple Data Tracker, and Public Information Page. They can reuse the shared Next.js source through `sourceTemplateSlug: "web-app"` while keeping their own names, descriptions, and database defaults.

Developer Starters expose the lower-level Custom Web App and API / Automation Service choices. Both target Azure App Service, but each carries its own runtime stack and feature support in catalog metadata. API / Automation Service defaults to no database, while the create flow still requires the user to explicitly choose Cedarville sign-in or openly public access.

Python `http.server` support is import-only for plain static repositories. Do not add it to the generated template catalog unless the product scope changes; imported static apps get runtime metadata during repository compatibility scanning and keep PostgreSQL and Microsoft Entra disabled.

`features.database` declares whether PostgreSQL is unsupported, optional, or required, plus the default provider. `features.entraLogin` is retained as legacy compatibility metadata for older saved requests and publishing paths that do not contain an explicit audience choice. For every current active generated template, the create form ignores the legacy mode and default, requires the user to choose either Cedarville sign-in or openly public access, and stores that choice on the request. Any new generated source engine must implement both choices before its templates are activated.

The seed script stores the user-facing decision metadata, runtime metadata, and feature metadata in `inputSchema` alongside the form fields so database rows stay aligned with the catalog.

## Manifest Rules

The template manifest at `templates/<slug>/template.json` defines which files are read from `files/` and which files are generated by portal code.

Use `conditionalEntryFiles` when a template file should only appear for a selected feature:

```json
"conditionalEntryFiles": {
  "databasePostgresql": ["prisma/schema.prisma.template"],
  "entraLogin": ["src/auth.ts.template"]
}
```

Use `generatedOverrides` when generation code intentionally owns a path that could also be represented by an entry file:

```json
"generatedOverrides": [
  "README.md",
  ".codex/skills/cu-app-portal/SKILL.md"
]
```

Generated overrides are intentional. When an entry file and generated override resolve to the same output path, the entry file is skipped and the generated content wins. This lets shared generation logic produce runtime-aware docs, deployment manifests, package files, and publishing skills while keeping static template assets for the parts that do not vary.

## Publishing Bundle

Push-to-deploy is the default for new managed app requests. Keep generated workflow assets manual-only at creation: the Azure publishing runtime adds the default-branch push trigger after resources and secrets are ready during the first explicitly requested publish. Its workflow commit uses `[skip ci]` to avoid a duplicate push deployment alongside manual dispatch. Generated documentation and app-local Codex guidance must describe automatic deployment as the default after first publish, with **Disable Auto-Deploy** for manual publishing and **Enable Auto-Deploy** to restore it.

Publishing-capable templates can include assets such as:

- `.github/workflows/`
- `.codex/skills/`
- `.codex/skills/cu-app-portal/`
- `.codex/skills/publish-to-azure/` as a compatibility redirect
- `docs/publishing/`

Current publishing-capable templates emit a generated deployment manifest at `app-portal/deployment-manifest.json` so generated-app fallback skills and portal-managed publishing flows can share the same deployment contract.

Every publishing-capable generated app must retain an exact public `GET /api/health` endpoint. It must return HTTP 200 when the app process is healthy and must not require an allow-list match, session, database, or external service. The portal uses this narrowly scoped endpoint to verify deployments when the app's normal route requires authentication.

When a later Codex change restricts an app's audience, it must use the portal-managed Cedarville Microsoft Entra sign-in flow, verify the user session, and enforce the requested restriction server-side. A client-only or standalone allow-list check is not sufficient.

Custom sign-in routes are allowed, but their exact route and required Entra callback route must remain anonymous. Portal deployment verification uses only the fixed `/api/health` endpoint and does not infer deployment success from an app's sign-in redirect.

Next.js publishing workflows provide a syntactically valid, non-production `DATABASE_URL` only to the GitHub Actions build step so Prisma can validate and generate the application without a live database. The portal-managed Azure App Service configuration remains the source of the real runtime connection string.

Publishing-capable templates should assume this direction:

- the portal renders the canonical source snapshot
- the portal-created GitHub repo is the supported publish source of truth

## Cedarville Login Pages

Next.js starters and presets are version 1.1.0 as of the custom-login update. When Cedarville sign-in is selected, include `src/app/login/page.tsx` and `src/lib/login-redirect.ts` through the template's `entraLogin` conditional entries. Public apps do not receive these files. FastAPI keeps its existing login flow.

Auth.js must set `pages.signIn` to `/login`. Exclude only the exact `/login` page from authentication middleware, alongside the existing required auth routes, public health check, and framework assets; `/login/private` and similarly named paths remain protected. The login button calls the server-side `signIn("microsoft-entra-id", { redirectTo })` in a Next.js server action. Keep the existing `/api/auth/callback/microsoft-entra-id` callback, secure sessions, and audience checks. Validate return destinations against `AUTH_URL`/`NEXTAUTH_URL`, fall back to `/`, and exclude login/auth destinations. Catch `AuthError` for a friendly retry message and rethrow other errors so framework redirects work.

Keep this pattern in the generated app skill and both generated/imported Codex handoffs. A browser link or form submission to `/api/auth/signin/microsoft-entra-id` reintroduces the warning-prone flow. A custom login page is a mitigation; production Chrome verification is still required before claiming a warning is resolved.

Existing generated Next.js sign-in apps with `templateVersion` older than 1.1.0 receive a notice at the top of both owner and admin app-details pages. Imported Next.js sign-in apps also receive it because repository preparation does not regenerate application code. The prompt checks the app's framework and existing fix before making changes. Public apps and FastAPI apps are excluded. Dismissal is per user and app in the current browser, and does not certify that the app was updated. The portal cannot detect later changes made directly in an app repository; users who already applied the fix can dismiss the notice. Blocked browser storage still allows dismissal for the current page, and clipboard failures expose the full prompt for manual copying.

No database migration, Azure setting change, or callback migration is needed for this update. New-app creation upserts the current catalog version; seeding also refreshes stored template metadata. Existing repositories are updated only when their owners use the prompt.

## Database Sync

Run `npm run prisma:seed` after catalog changes so the database template rows stay aligned with the in-code catalog used by the portal.
