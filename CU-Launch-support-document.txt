<h1>CU Launch</h1>
<h2>Solution Overview</h2>
<p>CU Launch is a new Cedarville University internal portal that enables staff to launch managed applications from approved templates, connect them to managed GitHub repositories, and publish supported applications through Azure App Service.</p>
<p>Primary users are Cedarville University staff. Tier 1 support is provided by User Services. Tier 2 support is provided by TechOps. The project developer supports application defects and unresolved technical issues.</p>
<p>CU Launch is a new function for Cedarville University and does not replace an existing solution.</p>
<p>Production URL: <a href="https://launch.cedarville.edu">https://launch.cedarville.edu</a></p>
<h2>Tier 1 Support Guidance</h2>
<h3>Support FAQ</h3>
<ul><li>Users must sign in with their Cedarville Microsoft Entra account.</li><li>Users can launch a new app from an approved template or add an existing app.</li><li>Users should follow the guided setup sequence and should not skip required confirmation steps.</li><li>Publishing is user-requested; creating a starter does not automatically publish it unless the user explicitly selects the publish option.</li><li>If an operation is still processing, users should wait for the status to update before retrying.</li><li>Users should capture the displayed support reference, error message, app name, and the step where the problem occurred.</li><li>Users should not delete repositories, Azure resources, or configuration as a first troubleshooting step.</li></ul>
<h3>Self-service Capabilities</h3>
<ul><li>Review the CU Launch user guide, quick start, FAQ, glossary, and troubleshooting documentation.</li><li>Create or import supported applications.</li><li>Continue incomplete setup from My Apps.</li><li>Retry publishing.</li><li>Repair publishing setup when credentials or configuration have changed.</li><li>Manage supported app resources from the app details page.</li><li>Manage notification preferences from Settings.</li></ul>

<h3>Escalation path and guidance</h3>
<p>User Services provides Tier 1 support through email, phone call, or ticket creation.</p>
<p>Escalate to TechOps when the issue involves Azure, Entra ID, GitHub integration, publishing, repository access, deployment failure, service configuration, or infrastructure.</p>
<p>Include the user’s Cedarville email address, app name, production URL, support reference, timestamp, exact error, affected workflow step, and any relevant screenshot.</p>
<p>Escalate to the project developer for application defects, portal behavior requiring code changes, or unresolved technical diagnosis.</p>
<h2>Tier 2 Support Guidance</h2>
<h3>Support FAQ</h3>
<ul><li>Verify whether the issue affects one user, one app, or multiple applications.</li><li>Confirm whether the failure occurred during authentication, repository creation/import, preparation, publishing, repair, retry, or resource deletion.</li><li>Check whether credentials, Entra configuration, GitHub App configuration, Azure configuration, or application settings have changed.</li><li>Confirm that the user is acting as the correct app owner or collaborator.</li><li>Do not treat a successful portal login as proof that delegated MCP or Azure publishing authorization is valid.</li><li>Confirm the exact public <code>/api/health</code> response when validating a deployed application; the expected contract is HTTP 200.</li></ul>
<h3>Test criteria</h3>
<ul><li>The portal loads at the production URL.</li><li>Cedarville Entra sign-in succeeds for an authorized user.</li><li>New-app and existing-app flows display correctly.</li><li>Approved templates can be selected.</li><li>Repository creation or import completes as expected.</li><li>Preparation and publishing statuses update correctly.</li><li>Retry and repair actions remain distinct.</li><li>Access controls prevent unauthorized users from managing app resources.</li><li>Published applications return HTTP 200 from <code>/api/health</code>.</li><li>Deletion remains scoped to the selected portal record, repository, Web App, and app-specific database.</li></ul>
<h3>Maintenance requirements</h3>
<ul><li>Maintain Microsoft Entra application credentials and issuer configuration.</li><li>Maintain GitHub App credentials, private key, installation configuration, and allowed organizations.</li><li>Maintain Azure App Service, PostgreSQL, and deployment configuration.</li><li>Keep template definitions, generated assets, publishing workflows, and support documentation synchronized.</li><li>Review notification delivery, audit events, publishing status, and failed operations.</li><li>Rotate secrets and certificates through managed secret stores or application settings.</li><li>Do not place secrets in tracked files, documentation, tests, or templates.</li></ul>
<h3>Restart /Refresh procedures</h3>
<ul><li>For users, refresh the current page after a status update delay.</li><li>For local development, restart the Next.js development server after configuration changes.</li><li>Restart local PostgreSQL through the documented Docker workflow when database connectivity is unavailable.</li><li>Re-run migrations or seeding only when the documented setup or maintenance process requires it.</li><li>For deployed services, use the applicable Azure App Service restart or redeployment procedure approved by TechOps.</li><li>Use Repair Publishing Setup when publishing prerequisites or credentials have drifted; use Retry Publish when prerequisites are valid and the deployment itself should be rerun.</li></ul>
